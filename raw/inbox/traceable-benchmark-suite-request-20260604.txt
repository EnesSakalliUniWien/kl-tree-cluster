Yes. I would build the next benchmark program as a traceable mathematical benchmark suite, not just more ARI tables. The repo already has a good starting point: cases are organized by source families such as Gaussian, dimensionality, outliers, binary, SBM, categorical, phylogenetic, and overlapping cases, and suites can be filtered by binary, categorical, continuous, discretized Gaussian, graph, or full.  ￼init￼.py￼ The generator contract already records source_family, feature_representation, and whether a case requires precomputed KL tree distances, which is exactly the metadata foundation needed for traceable benchmarks.  ￼

The missing step is to make every benchmark case answer a specific mathematical question: selected-tail calibration, internal support, MP/projection, categorical covariance, continuous covariance, traversal FDR, pass-through, phylogenetic null, or real-data evidence.

1. Benchmark design principles from the literature

The benchmark suite should not be a random collection of hard cases. A cluster benchmarking white paper argues that clustering benchmarking needs simulated and empirical data, clear target questions, neutral comparisons, and careful design because unsupervised methods lack a single universally accepted objective.  ￼ HAWKS makes the same point from another angle: synthetic clustering benchmarks should cover diverse properties that affect algorithm performance, and can even be generated to expose differences between specific algorithms.  ￼

Recent large-scale work also reinforces that clustering remains nontrivial even with many modern algorithms and data types. CLUBench reports a broad benchmark over 24 algorithms and 131 datasets across tabular, text, and image data, and emphasizes effects of data type, hyperparameter tuning, embeddings, and performance-matrix structure.  ￼ For graph clustering, PCBS emphasizes standardized, fine-grained evaluation of graph clustering quality and runtime across real-world graph datasets.  ￼

For KL-TE specifically, the most important benchmark principle is selection-aware traceability. Selective-inference papers on hierarchical clustering show that classical tests can be anti-conservative when clusters are selected by clustering before testing, and that the correct target is conditional on the clustering selection event.  ￼ This matches your selected-hierarchy problem exactly.

7. Metamorphic tests for traceability

Because clustering often lacks a unique oracle, add metamorphic tests. Metamorphic testing is designed for systems where exact expected outputs are hard to define; it checks necessary relations under input transformations.  ￼

Add these invariants:

Transformation	Expected behavior
Permute sample order	Same clusters up to labels
Permute feature order	Same decisions
Relabel categorical levels within each feature	Same decisions after feature-space relabel
Duplicate pure-noise features	Calibration should not become anti-conservative
Add null samples to all clusters proportionally	More stable support, not more false splits
Split a planted cluster into identical subclones	Should not over-split unless signal is added
Rotate continuous data under identity covariance	Same continuous decisions
Scale continuous covariance with whitening update	Same p-value calibration
Swap left/right children	Same sibling decision
Collapse signal to zero	\hat K\to 1, false split controlled

These tests are ideal for CI because they detect implementation and math-contract drift.

9. Priority order

Start with these five, because they will most improve method credibility:

1. Internal support threshold validation
    Protects production immediately.
2. Selected-tail law benchmark
    Directly addresses selected-hierarchy calibration.
3. Selected MP / k_{\min} / sibling dimension validation
    Stabilizes the projected-Wald layer.
4. Categorical simplex-boundary attribution
    Explains high-cardinality categorical failures.
5. Continuous low-rank/shrinkage covariance benchmark
    Opens the p\gg n continuous path honestly.

After that, do traversal/pass-through, phylogenetic nulls, and the locked manuscript evidence set.

10. The most important benchmark philosophy

Do not ask each benchmark only:

“Did ARI improve?”

Ask:

“Which mathematical contract did this benchmark validate or falsify?”

Every case should have:

benchmark_role
mathematical_target
expected_failure_modes
required_trace_columns
admissibility_rule
success_criterion

That will turn KL-TE from “a method with many diagnostics” into a traceable statistical system.
